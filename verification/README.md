# yapcasia.org 静的サイト コンテンツ同一性 検証レポート(統合版)

現行 yapcasia.org(本リポジトリを GitHub Pages で配信し、Cloudflare を前段に置いたもの)と旧サーバーのコンテンツが同一に保たれているかを検証した結果をまとめる。判定基準は「URL の完全一致」ではなく「同じリンク先から同じコンテンツが取得できること」を優先した。

このレポートは、基準の異なる 2 つの検証を統合したものである。

- **検証 A(Wayback 基準、初版)**: 実行環境から旧サーバーに到達できなかったため、Wayback Machine の CDX 索引から「旧サイトが 200 を返していた URL」1,724 件を集め、現行サイトへの HTTP プローブと当時のスナップショットとの本文比較を行った。
- **検証 B(旧サーバー基準)**: 旧サーバー(133.242.211.35、`Host: yapcasia.org`)に直接到達できる環境で、リポジトリと旧サーバーのリンクから集めた URL を両側から取得して比較した。検証 A の CDX 一覧も URL 集合に加え、両基準で同じ集合を見られるようにした。

- 生成日: 2026-09-10
- 対象: 4,909 URL(リポジトリ 3,536・Wayback CDX 1,798・旧サーバーと現行サイトのリンク抽出・転送先を合わせたもの。同一ファイルの `x.html` と `x` は別 URL として数える)
- 併記データ:
  - `url-status.csv` — 4,909 URL すべての旧サーバー(現在)・現行・Wayback の状態と判定
  - `url-gaps.csv` — 検証 A が「現行で 404」とした旧 URL 221 件に、旧サーバーの現在の応答と再判定を付けたもの
  - `restore-candidates.csv` — 現行に無いコンテンツ 279 件を「旧サーバーから取得できる」「Wayback にしか無い」に分けた一覧

## 0. 結論(サマリ)

- **既存ページの本文は保たれている。** 旧サーバーで 200 を返す 3,057 URL のうち、現行でも 200 を返す 2,856 URL は、バイト一致(779)か、内容を変えない既知の変換(自己参照 URL のルート相対化、Google の legacy loader の直接参照化、互換 JavaScript の注入など)で全差分が説明できるものが大半である。残る差分の中心は 2015 年の動的ページ 83 ページで、**食い違いの原因は旧サーバー側の劣化**である(2014 年用テンプレートで描画されており、Wayback の 2016〜2017 年のスナップショット 25 件はいずれも現行サイトと一致した)。
- **現行で取得できない旧コンテンツは、旧サーバーに現存するもの 201 URL と、旧サーバーからも消えて Wayback にしか無いもの 78 URL に分かれる。** 前者の内訳は、採択トーク一覧に載らない応募トーク 86、メンバー個別ページ 81、2011 年のニュース 9、2010 年 2、2014 年チケット案内 1、動的エンドポイント 20、言語別 index 2 である。検証 A が「孤立 URL」とした 152 件の 129 件は旧サーバーに現存しており、**旧サーバーが生きているうちなら復元できる**。後者の主なものは 2013 年スピーカー個別ページ 15 件(現行の 10〜53 ページからリンクされている)と 2013・2014 年の individual_sponsors(各年のほぼ全ページからリンク)で、これらは旧サーバーでも 404/500 なので **Wayback からしか復元できない**。
- **旧 `/index.html` にあった年度横断のポータルページは失われている**(現行は 2015 年トップの複製。既存計画では意図的な決定 D-14)。
- **移行作業そのものが持ち込んだ不具合がある。** はてなブックマークのリンク破損(234 ページ・571 箇所)、OGP の URL の相対パス化(約 900 ページ)、http のままの共有ウィジェット読み込み(約 820 ページ、https では遮断)、`<base href="">`(81 ページ)、第三者のログイン画面を保存した残骸(10 URL)。§6 に詳細と対応案をまとめた。

## 1. 検証方法

### 1.1 検証 A の制約と、検証 B での解消

検証 A の実行環境では、指示の `curl --resolve yapcasia.org:80:133.242.211.35 ...` が機能しなかった。外向きプロキシが Host ヘッダーを再解決するため、`Host: yapcasia.org` のリクエストは常に Cloudflare(現行サイト)へ転送され、旧サーバーの yapcasia vhost には届かない(旧 IP 自体は到達可能だが既定 vhost が perldoc.jp になっている)。そこで検証 A は Wayback Machine を参照元とし、CDX から `statuscode:200` かつ `text/html` の URL を年別に集め(1,789 URL、トラッキングパラメータ正規化後 1,724)、会期当時のスナップショットと現行のファイルをテキスト比較した。

検証 B の環境では同じ curl が旧サーバーに届く(`/` が `/2015/` へ 302、`/2015/` が 36,441 バイトの旧テンプレート、nginx/1.6.2)。旧サーバーの応答は Accept-Language(ja / en / fr / なし)と User-Agent(iPhone)を変えても変わらないことを確認したうえで 1 変種だけ取得し、差分が残った 830 URL は時間を置いて再取得して不安定さを調べた(2014 年ページのアバターが取得のたびに出たり消えたりする。538 ページ中 71 ページで応答が変わった)。

Wayback は「稼働中の旧サーバーの現在の状態」ではなく過去スナップショットの集合であり、旧サーバーからも後に消えた URL を含む。逆に、旧サーバーからのリンク抽出だけでは、どこからもリンクされていない応募トークやメンバーページは見つからない。両者を合わせることで、本レポートは「現在の旧サーバーにあるもの」と「当時あったもの」の両方を対象にしている。

### 1.2 URL 集合(4,909 URL)

1. リポジトリの全ファイルから導いた URL。`a/b.html` からは `/a/b.html`・`/a/b`、`index.html` からはディレクトリ URL、wget 形式の `x@lang=en.html` からは元のクエリ URL `x?lang=en` も生成した
2. 年度ルート `/2005/`〜`/2017/`、`/`、`/latest/photos`、404 プローブ
3. 検証 A の CDX 一覧(1,798 URL)
4. 旧サーバーの 200 応答から抽出したリンク(href / src / action / srcset / data-* / meta refresh / インライン style と `<style>` の `url()` / `<script>` 内のパス文字列 / CSS の `url()` と `@import` / atom.xml のエスケープ済み HTML 内のリンク。HTML コメント内も含む)
5. 現行サイトのページから抽出したリンクと、両側の転送先

### 1.3 比較

取得は旧が HTTP/1.1 で Host ヘッダー付き、現行が https 経由。転送は同一ホスト内で最大 8 段追い、最終応答どうしを比較した。比較は 3 段階で行う。まずバイト一致を見る。次に HTML を正規化して行単位で diff を取り、ハンクごとに分類する。正規化は、空白・引用符・自己終了タグ・属性順の吸収、URL 属性の絶対パス化(`.html` の有無、末尾の `/`、`index.html` を同一視)、`http://yapcasia.org` 自己参照のルート相対化、外部 URL の http/https の吸収である。コメント、外部 URL のスキーム、自己参照 URL の書式だけの差は「benign」として本文差から分けた。最後に、新旧でリンク先 URL が変わった組については、「旧のリンク先を旧サーバーから取った内容」と「新のリンク先を現行から取った内容」を同じ手順で比較した。

旧サーバーの劣化が疑われるページは、Wayback の原本(`id_` 付き URL)を取得して旧・現行・Wayback の三者で比較した。現行サイトの実際の挙動は、ブラウザーで 2014 年のトークページを開いてコンソールの Mixed Content エラーを読んで確かめた。

### 1.4 現行サイトの配信挙動(判定に必要な前提)

現行サイトは GitHub Pages の前段に Cloudflare があり、クエリ付き URL を `path?key=val` → `path@key=val.html` に書き換えて配信する(該当ファイルがある時のみ 200)。`b.html` があれば `/a/b` も 200 になる。このためリンク到達性の判定はファイルシステムではなく実サイトへの HTTP プローブで行った。

## 4. 本文の一致(旧サーバー基準)

### 4.1 内容を変えない既知の変換(982 URL・766 ページで全ハンクを説明)

| 変換 | ハンク数 | 確認したこと |

### 4.2 旧サーバー側の劣化(2015 年の 83 ページ)

残差 98 ページのうち 83 ページは `/2015/talk/show/` 68、`/2015/talk/schedule` 系 12、`/2015/talk/list` 2、`/2015/vote/form` 1 である。旧サーバーは現在これらを 2014 年用のテンプレートで描画している。`<title>` がトーク名を含まず「YAPC::Asia Tokyo 2015」だけになり、`og:title` は「... - YAPC::Asia Tokyo 2014」、会場名は「Main Hall (Fujiwara Hiroshi Hall)」「Multipurpose Room 2」(2014 年の慶應日吉)で、現行の「トラックA 国際会議場」「トラックB (701-702)」(2015 年のビッグサイト)と食い違う。日付リンクも `/2014/talk/schedule?date=2014-08-28` を指し、通訳の有無や採択状態の表示がない。

Wayback の 2016〜2017 年のスナップショットとの三者比較(正規化後の行数。コメントと URL 書式の差は除く)では、25 ページすべてで現行サイトが当時の内容と一致した。現行側の 1 行差は canonical リンクの追加である。

|---|---:|---:|

| `/2015/talk/schedule?date=2015-08-20` / `21` / `22` | 569 / 262 / 314 行 | 1 / 1 / 1 行 |

2015 年トークページの slideshare リンクも同じ事情で、旧サーバーは `slideshare.net/slideshow/<slug>/<id>` という現在の書式を返し(アプリが描画時に oEmbed を引いていると考えられる)、現行と Wayback は `slideshare.net/<user>/<slug>` で一致する(EXT_LINK_DIFF のうち 47 件)。2014 年についても、旧サーバーはアバター画像をプレースホルダーに置き換えて返すが、Wayback 2016 年には画像がある。現行は旧より Wayback に近いが、一部のアバター(twimg 由来)は現行でも欠けている。

### 4.3 その他の残差

- 2014 年の 11 URL(`/2014/talk/schedule` の日付なし・`?format=mobile`、`/2014/talk/list?status=rejected` など): 差はページ内アンカーの書式だけで、旧の `href="#top"` が現行では `schedule?date=2014-08-30#top` のように自ページの URL 付きになっている。内容は同じ
- CSS 6 本(2012 `html.css`、2013 `style.css`、2014 `bootstrap.css`・`yapcasia-ui.css`、2015 `foundation.css`・`html.css`): minify と、フォント URL の書式(`/2012/static/fonts/x.eot` → `../fonts/x.eot`、`x.eot?#iefix` → `x.eot@`)、`fonts.googleapis.com` の https 化を吸収すると一致する(§6.7)

## 5. リンク先の変化

新旧でリンク先 URL が変わった組は 289 組あり、内容の対応を確かめた。

- `/2015/talk/schedule?date=2015-08-2X`(旧のリンク先)→ `/2015/talk/schedule-2015-08-2X-pc`(現行のリンク先): 現行サイト内で両 URL の応答はバイト一致(旧サーバー側の内容とは §4.2 の理由で一致しない)
- `/2014/talk/list` → `/2014/talk`: 現行は 301 で `/2014/talk/list` に戻るので同一
- `/2011/talk/NN?lang=en` → `/2011/talk/NN@lang=en`: 現行サイト内で両者はバイト一致。ただし内容は日本語版と同じで、英語版は旧サーバーも Wayback 2012〜2013 年も返していない(`?lang=` は無視されている)
- 旧の 2015 年ページが `/2014/member/show/UUID` を指している 151 組は旧の劣化(旧のリンク先は 500)で、現行は `/2015/member/show/UUID` を指す
- `/2010/` の JPA ロゴ画像を外部(`japan.perlassociation.org`、https は 404)からローカルの `/2010/images/logo-jpa.png` に置換

現行サイトの HTML から抽出した同一ホスト内のリンク先 2,811 件のうち 200 にならないものは 325 件で、旧サーバーで 200 だったものは 10 件、すべて §3.1 の動的エンドポイント(`/2015/member` は 544 ページ、`/2014/member/` 系は 544 ページから)である。残りの 315 件は旧サーバーでも 404 か 500 で、そのうち Wayback にあるものは §3.2 に含めた。旧のページにあって現行の同じページから消えたリンクは 980 本あり、リンク先はすべて現行でも URL のまま 200 で取得できる(言語切替リンク `/2011/talk/?lang=ja` が 391 ページ、2015 年の日付別スケジュールへのリンクが `-pc` 形式に置き換わったものなど)。

## 6. 移行作業が持ち込んだ不具合

以下は旧サーバーでは起きておらず、現行サイトで新たに生じているものである。

### 6.1 はてなブックマークのリンク破損(234 ページ・571 箇所)

`http://b.hatena.ne.jp/entry/http://yapcasia.org/2014/...` の内側の `http://yapcasia.org` まで削られ、`http://b.hatena.ne.jp/entry//2014/...` になっている(2012 年 1、2013 年 8、2014 年 117、2015 年 108 ページ)。自己参照をルート相対にした置換が外部 URL の中にも当たったものと考えられる。旧サーバーで 200 を返した他の外部リンク(conferences / tokyo / tokyo2007 / video の各サブドメイン 6,600 箇所以上)は影響を受けていない。

### 6.2 OGP の URL の相対パス化(約 900 ページ)

`og:url` と `og:image` の content が `/2015/assets/...` のようなルート相対パスになっている(2011 年 158、2012 年 65、2013 年 164、2014 年 261、2015 年 257 ページ。2012 年の 363 ページは絶対 URL のまま)。旧は絶対 URL である。OGP のスクレイパーは相対パスを解決しないので、共有時のプレビュー画像と URL が失われる。同様に Twitter 共有ボタンの `data-url` と Facebook の `data-href` も相対パスになっている(2013 年 8、2014 年 117、2015 年 108 ページ)。

### 6.3 共有ウィジェットの http 読み込み(約 820 ページ)

2012〜2015 年のページ内スクリプトが、はてな・mixi・Twitter・Facebook のウィジェットを `src: "http://..."` で読み込んでいる(2012 年 149、2013 年 149、2014 年 261、2015 年 257 ページ。旧サーバーの同じページも http だが、旧は http 配信なので読み込めていた)。https の現行サイトでは Mixed Content として遮断され、共有ボタンが描画されない。ブラウザーで `/2014/talk/show/a02d05e6-...` を開くと、コンソールに 4 本の script と Google+ の iframe についての「This request has been blocked」が出ることを確認した。`<img src="http://...">`(はてな・twimg・gravatar など)は Chrome が https へ自動昇格するので表示される。

### 6.4 `<link rel="canonical">` の相対パス(2015 年 102 ページ)

現行で追加された canonical が `/2015/talk/show/...` の相対パスになっている。旧にはないので比較上の損失ではないが、絶対 URL が望ましい。

### 6.5 `<base href="">`(2010 年トークページ 81 ページ)

旧の `<base href="http://yapcasia.org/2010/">` が `<base href="">` になっている。wget がリンクをページ基準の絶対パスに書き換えているので、抽出したリンク 2,811 件の検査では退行は見つからなかったが、JavaScript などから相対 URL を解決する箇所があれば挙動が変わる。

### 6.6 第三者のログイン画面の残骸(10 URL)

`/2014/auth/auth_fb`、`/2014/auth/auth_github`、`/2015/auth/auth_fb`、`/2015/auth/auth_github`、`/2015/auth/auth_twitter`(それぞれ `.html` 付きも)が、旧の OAuth 転送先(Facebook / GitHub / Twitter)の応答を保存した HTML を 200 で返す。タイトルは「ブラウザーをアップデートしてください | Facebook」「Sign in to GitHub · GitHub」「Twitter / アプリケーション認証」である。

### 6.7 wget の保存名に依存したフォント URL

CSS の `x.eot?#iefix` が `x.eot@` に書き換えられ、`x.eot@` というファイルが 8 本リポジトリにある。動作はするが、通常の配信では意図しない形である。

### 6.8 旧サーバーで 403 だった 22 のトークページが公開されている

`/2015/talk/show/` の 22 ページ(例: `06da17f0-3dc5-11e5-b91a-76d67d574c3a`「吉祥寺.pmというイベントを作った話」)は旧サーバーが 403 を返すが、現行は「Accepted」の表示付きで 200 を返す。Wayback 2016 年にはこのうち確認した 1 ページが 200 で存在するので、当時は公開されていた可能性が高い。403 の理由は旧アプリ側の事情と考えられるが、公開してよいかは確認しておいたほうがよい。§3.1 の応募ページ 86 件を復元するかどうかも同じ判断に含まれる(検証 A の「保存対象とするかは方針判断」)。

## 7. 対応の優先順位(案)

1. **旧サーバーが生きているうちに取得する**: `restore-candidates.csv` で `obtainable_from = old-server` かつ `note` が空の 179 URL(§3.1)。公開の是非を決める前に取得だけ済ませておけば、後から判断できる。
2. **Wayback から復元する**: 2013 年スピーカー個別ページ 15 件、`/2013/individual_sponsors/`、`/2014/individual_sponsors/`、`/2013/event/show/bfc556ec-...`、`/2012/member/show/0f9c5310-...`、2010 年トップからリンクされる 5 URL(§3.2 のうち現行ページからリンクされているもの)。
3. **現行サイトの不具合を直す**: はてなブックマークの URL(§6.1)、OGP と共有ボタンの絶対 URL 化(§6.2)、共有ウィジェットの https 化(§6.3)、認証ページの残骸の削除(§6.6)。
4. **方針を決める**: 応募トーク・メンバーページの公開(§3.1、§6.8)、旧 `/index.html` ポータル(§3.4)、`/2009/photos.html` の転送先(§3.5)、`/2015/member/show/` を Wayback の当時の内容に戻すか(§4.2)。
